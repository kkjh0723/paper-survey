제출: 2026년 9월 17일 (v1) · 시뮬레이터 RoboCasa (PandaOmron 로봇) · 코딩 모델 gpt-6-astra (high reasoning) · 코드/프로젝트 페이지 공개 링크 없음

한 줄 요약 (TL;DR)

로봇 제어 정책을 신경망 가중치가 아니라 파이썬 코드로 만든다. 코딩 에이전트(LLM이 코드를 쓰고 실행 결과를 보고 고치는 자동화 도구)가 시연 10개로 첫 코드를 만들고, 시뮬레이션 실행 피드백으로 5세대까지 고친다. 이렇게 소스 태스크 4개(수도꼭지 끄기·서랍 열기 등)에서 평균 Test 성공률이 28.3%→64.2%로 오른다. 개선된 코드들은 "소프트웨어 아카이브"(태스크별 완성 코드 폴더 모음)에 저장된다. 새 태스크 9개에서 이 아카이브를 참고하게 하면, 3회 반복 평균 성공률이 57.0%였다. 참고 코드가 없을 때는 45.2%, 개선 전 초기 코드를 참고할 때는 41.5%였다. 즉 "실행 경험으로 다듬어진 코드"가 새 정책을 만드는 재료로서 가치가 있다. 다만 9개 중 2개 태스크에서는 초기 코드 참고가 더 나았다.

1배경 · 문제의식

폐루프(closed-loop) 정책은 매 스텝 새 관찰을 보고 행동을 다시 정하는 제어기다. 이를 코드로 짜려면 세 가지가 필요하다. 물체 인식 같은 관찰 처리, "지금 잡는 중인가/옮기는 중인가" 같은 상태(phase) 관리, 그리고 상황별 조건 분기다. 태스크마다 사람이 이를 설계·튜닝하는 비용이 크다.

Code as Policies(LLM이 인식·제어 API를 호출하는 프로그램을 생성해 정책으로 쓰는 접근) 이후, 실행 피드백으로 제어 코드를 다시 쓰는 연구가 늘었다. 이런 연구는 코드를 "경험으로 갱신되는 정책 표현"으로 본다. 그렇다면 신경망 가중치가 새 태스크 학습의 출발점이 되듯, 개선된 코드도 새 태스크의 재료가 될 수 있는가?

문제는 이것이 자명하지 않다는 점이다. 최적화 중 추가된 조건 분기와 제어 루틴은 소스 태스크 조건에 과특화(over-specialized)될 수 있다. 그러면 오히려 다른 태스크로의 전이를 방해한다. 기존 연구는 계획(planner) 수준 코드만 저장하거나(MTP, Memory Transfer Planning), 경험을 "스킬 함수"로 따로 추출해 저장했다. 반면 관찰 처리·상태 관리·조건 로직을 모두 포함한 완성 구현 전체를 저장해 참고시키는 것의 가치는 검증되지 않았다.

2핵심 Contribution

  • 실행으로 개선된 로봇 소프트웨어의 전이 연구 — 소스 태스크에서 실행 피드백으로 최적화한 폐루프 구현 전체가 새 태스크 정책 획득의 참고 자료로 유용한지를 체계적으로 검증.
  • 실행 기반 코드 최적화 — RoboCasa 소스 태스크 4개에서 반복 최적화로 평균 Test 성공률 28.3%→64.2%(+35.8%p). 관찰 입력 ablation으로 GT-Geom(시뮬레이터가 주는 정답 물체 분할 마스크+이름표)이 가장 중요한 입력임을 확인.
  • 소스 성능 vs 전이 가능성 분리 비교 — 새 태스크 9개 × 독립 3회 실행에서 "참고 없음 / 초기 코드 참고(Initial4) / 최적화 코드 참고(Best4)"를 비교. Best4가 3회 모두 9태스크 평균에서 Initial4를 앞섬(평균 +15.6%p). 반면 Initial4는 참고 없음보다도 낮아, "기존 코드에 접근하는 것만으로는 부족하고 코드의 최적화 단계가 중요하다"는 결론.

3Method

3-1. 정책 인터페이스: 코드로 된 폐루프 정책

직관: 정책은 "관찰 + 내부 기억 → 행동 + 갱신된 기억"을 계산하는 평범한 프로그램이다. 학습 대상은 모델 가중치가 아니라 이 코드와 설정 파일이다.

식 (1)은 두 줄이다. 첫 줄은 "시뮬레이터 상태에서 허용된 관찰만 꺼낸다"는 뜻이다. 둘째 줄은 "관찰과 내부 상태를 받아 행동과 다음 내부 상태를 낸다"는 뜻이다.

ot = 𝒪ω(xt),   (at, ht+1) = P(ot, ht; q)

  • xt: 시점 t의 시뮬레이터 전체 상태. ω: 관찰 구성(어떤 센서를 허용할지). 최적화 중 고정.
  • ot: 정책이 실제로 보는 관찰. at: 제어기 명령(행동).
  • ht: 내부 상태(예: 현재 조작 단계가 "접근/파지/이동" 중 무엇인지). 에피소드 시작마다 초기화.
  • q: 조작 태스크. 정책은 태스크별 시간 한도 Hq 안에 성공 조건을 만족해야 함.

코딩 에이전트 𝒜B는 태스크 지시문, 성공 시연 𝒟q, 관찰–행동 인터페이스 명세 ℐω를 받는다(B는 생성 예산). 결과물은 policy.py, perception.py, config.yaml 등으로 이뤄진 실행 가능한 정책 패키지다. 완성된 정책은 실행 중 LLM을 전혀 호출하지 않는다.

소스 태스크의 초기 상태 케이스들은 서로 겹치지 않는 세 묶음으로 나뉜다. Train은 코드 수정용 실행 경험을 준다. Validation은 후보 코드 비교·선택에 쓰인다. Test는 선택된 최종 코드의 평가에만 쓰이고, 수정에는 절대 쓰이지 않는다.

3-2. 소스 태스크에서 최적화하고 보관하기

직관: 사람이 디버깅하듯, 실행 → 실패 로그 확인 → 코드 수정을 반복한다. 가장 잘 일반화된 버전(Validation 기준)만 남긴다.
  • 초기 코드 Ps(0): 성공 시연·지시문·인터페이스로 생성. 목표는 시연 재생(replay)이 아니라, 새 관찰에 반응하는 정책이다.
  • 피드백 비대칭: Train에서는 관찰·행동·성공 여부·실행 에러를 모두 준다. Validation에서는 성공 횟수 집계만 준다(이미지·궤적 없음). Validation에 맞춰 코드를 억지로 끼워 맞추는 것을 막기 위함이다.
  • 에이전트는 관찰 처리, 제어 파라미터, 조건, 상태 전이를 수정한다. 매 수정은 지금까지 평가된 최고 후보에서 출발한다.

식 (2)는 "K세대(초기 생성 포함) 후보 중 Validation 성공률이 가장 높은 코드를 고른다"는 뜻이다.

Ps★ ∈ argmaxP ∈ {Ps(0),…,Ps(K−1)} Ĵ𝒞sval(P)

여기서 Ĵ𝒞(P)는 케이스 집합 𝒞에서 정책 P의 성공률이고, 𝒞sval은 소스 태스크 s의 Validation 케이스다. 선택된 코드들의 모음이 아카이브 ℳ = {Ps★ | s ∈ 𝒮}다. 실행에 필요한 코드와 자산만 저장한다. 소스 실행 로그나 평가기 내부는 저장하지 않는다. 또한 "재사용 스킬"로 따로 정제하지 않고 구현 전체를 그대로 둔다.

3-3. 아카이브 참고로 새 태스크에 전이하기

직관: 숙련 개발자가 비슷한 기존 프로젝트 코드를 열어 보고, 필요한 부분만 가져와 고치는 방식이다. 어떤 코드를 볼지는 에이전트가 스스로 정한다.

식 (3)은 "새 태스크 q의 초기 정책을, 기존 입력에 아카이브까지 더해 생성한다"는 뜻이다.

P̃q(0) = 𝒜B(q, 𝒟q, ℐω, ℳ)

  • 아카이브는 읽기 전용이다. 작업 공간에 자동 복사되지 않는다.
  • "이 소스가 이 타깃에 대응한다" 같은 매핑을 주지 않는다. 무엇을 열어보고 재사용·조합·수정할지는 에이전트가 결정한다.
  • 초기 정책을 타깃 Train 케이스에서 실행하고, 궤적과 결과를 돌려받아 개선한다. 최종 정책은 고정(frozen) 후 Test로 평가한다.

  • Initial4(41.5%)는 No reference(45.2%)보다도 낮다. 즉 덜 다듬어진 코드를 참고하면 오히려 방해가 될 수 있다.

코드 복잡도 분석 (전이 역전의 원인 탐색)

  • 참고 코드의 if/elif 문 총수(테스트 코드 제외)는 Initial4 622개에서 Best4 741개로 늘었다(+19.1%). 4개 구현 모두 증가했고, 전자레인지 켜기 코드는 138→225개로 가장 많이 늘었다.
  • 저자 해석은 이렇다. 상황별 분기는 소스 성공에는 도움이 되지만, 새 태스크에서는 수정이 필요할 수 있다. 그래서 가장 유용한 참고 코드는 "최적화 단계"와 "타깃 개선 반복 횟수" 둘 다에 달려 있을 수 있다. 다만 분기 수 증가만으로 과특화가 입증되지는 않는다고 명시한다.

한계

  • 모든 실험이 시뮬레이션이며, 실로봇에서는 검증되지 않았다. 실세계에서는 GT-Geom 대신 Depth Anything V2(깊이 추정)나 SAM 2(분할 모델) 같은 추정기로 대체해야 한다.
  • 소스 아카이브는 한 번만 만들어 고정했다. 따라서 소스 코드 획득 자체의 변동성은 평가되지 않았다. 일부 타깃은 실행 간 편차가 크다(예: ±52.0).
